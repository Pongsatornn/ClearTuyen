# Feature Ideas — fridge-menu

วิธีอ่านไฟล์นี้: เริ่มจาก persona จริงที่ระบบตอนนี้รองรับอยู่ (อ้างอิงจากโค้ด/schema ที่มีจริง ไม่ใช่เดาเอง) →
ดูว่าแต่ละคนพยายามทำอะไรให้สำเร็จ (JTBD) แล้วระบบขาดตรงไหน → ค่อยเสนอฟีเจอร์แก้ช่องว่างนั้น → จัดลำดับความคุ้มค่า

---

## 1. Persona ของระบบนี้ (อ้างอิงจากโค้ดที่มีจริง)

โปรเจกต์นี้ไม่มีระบบ auth/role จริง ทุกคนใช้ UI หน้าเดียวกันหมด แต่จากการไล่ feature ที่มีอยู่ (`IngredientInput`/`ImageUpload`,
`SavedRecipes`, `ChefChat`) แยกได้ 3 กลุ่มพฤติกรรมการใช้งานที่ชัดเจน:

### Persona A — "คนล้างตู้เย็น" (ผู้ใช้หลัก ตรงกับชื่อโปรดักต์และเป้าหมายใน `AI_CHEF_SPEC.md` ข้อ 2 "ลดขยะอาหาร")
- **คือใคร:** คนที่เปิดตู้เย็นแล้วเจอวัตถุดิบเหลือๆ ไม่รู้จะทำอะไรกิน ไม่อยากออกไปซื้อของเพิ่ม
- **ต้องการ:** พิมพ์/ถ่ายรูปวัตถุดิบที่มี → เลือกแนวอาหาร → ได้สูตรที่ทำได้จริงจากของที่มีอยู่
- **หลักฐานในโค้ด:** `IngredientInput.tsx`, `ImageUpload.tsx` (เรียก `/api/vision`), `CuisineSelector.tsx`, `/api/generate-recipe` ที่ system prompt เขียนตรงๆ ว่า "ห้ามเพิ่มวัตถุดิบหลักที่ไม่มี"

### Persona B — "นักสะสมสูตรอาหาร"
- **คือใคร:** คนที่เจอเมนูที่ชอบจากการล้างตู้เย็นครั้งก่อน แล้วอยากเก็บไว้ทำซ้ำวันหลัง
- **ต้องการ:** กดบันทึกเมนู แล้วย้อนกลับมาดูรายการที่เคยบันทึกได้
- **หลักฐานในโค้ด:** ปุ่มหัวใจใน `RecipeCard.tsx` → `saveRecipe()` ใน `lib/supabase.ts`, component `SavedRecipes.tsx` ที่มีไว้เพื่อดูรายการนี้โดยเฉพาะ

### Persona C — "มือใหม่ที่ไม่มั่นใจระหว่างทำ"
- **คือใคร:** คนที่ได้สูตรมาแล้วแต่ระหว่างทำจริงเจอปัญหา (ของหมด/ไม่แน่ใจขั้นตอน) และอยากถามสดๆ
- **ต้องการ:** ถามคำถามเกี่ยวกับสูตรที่กำลังทำระหว่างครัว ไม่อยากไปเปิด Google แยก
- **หลักฐานในโค้ด:** `ChefChat.tsx` ที่มี placeholder ตรงๆ ว่า `"ถ้าไม่มีน้ำปลาใช้อะไรแทน?"` และ `/api/chat` ที่ผูก system prompt กับสูตรที่กำลังเปิดอยู่

> หมายเหตุ: กลุ่ม "คนดูแลสุขภาพ" (ที่อาจเลือก cuisine "เพื่อสุขภาพ" หรือดู calories/protein ใน `RecipeCard`) ไม่ได้แยกเป็น persona
> ต่างหาก เพราะไม่มี flow/หน้าจอเฉพาะให้ — เป็นแค่ "โหมด" หนึ่งของ Persona A ที่ใช้ UI เดิมทั้งหมด

|---|---|---|---|
| C1 | ถามคำถามเกี่ยวกับสูตรที่กำลังทำ | ✅ รองรับเต็มที่ | - |
| C2 | ได้คำตอบที่รู้ว่าตัวเองมีวัตถุดิบอะไรอยู่จริง (ไม่ใช่แค่รู้ชื่อสูตร) | ⚠️ รองรับครึ่งเดียว | `ChefChat` ส่งแค่ `recipeName` + `recipeSteps` ไปที่ `/api/chat` — ไม่ส่ง `ingredientList` ที่ผู้ใช้กรอกไว้ตอนแรก AI จึงตอบคำถามแบบ "ถ้าไม่มีน้ำปลาใช้อะไรแทน" แบบทั่วไป ไม่รู้ว่าจริงๆ ผู้ใช้มีอะไรอยู่ในตู้เย็นบ้างที่เอามาแทนได้เลย |

## 3. ฟีเจอร์ที่เสนอ (โยงกลับช่องว่างข้อ 2 ทุกอัน)

### F1. แสดง "มีอยู่แล้ว" vs "ต้องซื้อเพิ่ม" ในสูตร
- **แก้ปัญหาของ:** Persona A (A3)
- **ทำไมอยากได้จริง:** ตอนนี้ผู้ใช้เห็นรายการวัตถุดิบในสูตรแล้วต้องนั่งไล่เทียบเองว่าอันไหนมีอยู่แล้ว อันไหนต้องซื้อเพิ่ม — ทั้งที่ AI บอกไว้แล้วในข้อมูล (`is_staple`) แค่ไม่ถูกโชว์ นี่คือ friction ที่แก้ได้ทันทีโดยไม่ต้องเปลี่ยน backend เลย
- **ความยาก:** **ง่าย** — แก้แค่ `components/RecipeCard.tsx` เพิ่ม badge/ไอคอนตาม `ing.is_staple` ที่มีอยู่แล้วใน response ไม่ต้องแตะ AI prompt, schema, หรือ DB

### F2. รีเซ็ตบทสนทนา ChefChat เมื่อเปลี่ยนสูตร
- **แก้ปัญหาของ:** Persona C (C3)
- **ทำไมอยากได้จริง:** ไม่ใช่ฟีเจอร์ใหม่ แต่เป็นการปิด bug เชิง UX ที่ทำให้ persona B/A ที่กดขอเมนูใหม่ (F5 ด้านล่าง หรือปุ่มเดิมซ้ำ) แล้วเจอ ChefChat ทักทายผิดเมนู ดูไม่น่าเชื่อถือ
- **ความยาก:** **ง่ายมาก** — ใส่ `key={recipe.recipe_name}` ให้ `<ChefChat />` ใน `app/page.tsx` บรรทัดเดียว บังคับให้ component mount ใหม่พร้อม state สะอาด

### F3. ให้ ChefChat รู้ว่าผู้ใช้มีวัตถุดิบอะไรอยู่จริง
- **แก้ปัญหาของ:** Persona C (C2)
- **ทำไมอยากได้จริง:** ตอบคำถาม "แทนน้ำปลาด้วยอะไรดี" แบบรู้ว่าผู้ใช้มีซีอิ๊วอยู่แล้วในตู้เย็น (เพราะพิมพ์ไว้ตอนแรก) มีประโยชน์กว่าคำตอบทั่วไปที่ลอกมาจากอินเทอร์เน็ตเยอะมาก ตรงกับ core value ของแอป (ใช้ของที่มีจริง)
- **ความยาก:** **ง่าย** — `state.ingredientList` มีอยู่แล้วใน `app/page.tsx` แค่ส่งเป็น prop เพิ่มให้ `ChefChat` แล้ว forward เข้า body ของ `/api/chat`, เพิ่ม 1 บรรทัดใน system prompt ของ `route.ts`

### F4. เก็บรายการวัตถุดิบไว้ใน localStorage ระหว่างเซสชัน
- **แก้ปัญหาของ:** Persona A (A6)
- **ทำไมอยากได้จริง:** พฤติกรรมจริงคือคนพิมพ์วัตถุดิบไปแล้วอาจต้องปิดแท็บ/สลับแอประหว่างทาง (เช่นไปถ่ายรูปเพิ่ม) กลับมาแล้วของหายหมดต้องพิมพ์ใหม่ทั้งชุด น่ารำคาญและอาจทำให้เลิกใช้กลางคัน
- **ความยาก:** **ง่าย** — pattern เดียวกับที่มีอยู่แล้วใน `lib/supabase.ts` (`getAnonymousUserId` ใช้ `window.localStorage`) แค่เพิ่ม `useEffect` sync `ingredientList` เข้า/ออก localStorage ใน `app/page.tsx`

### F5. ปุ่ม "ขอเมนูอื่น" ที่กันไม่ให้แนะนำซ้ำ
- **แก้ปัญหาของ:** Persona A (A4)
- **ทำไมอยากได้จริง:** ทำเป็นปุ่มแยกให้ชัดว่านี่คือ "ไม่เอาเมนูนี้ ขอใหม่" (ตอนนี้ทำได้แต่ซ่อนอยู่ ไม่มีใครเดาว่ากดปุ่มเดิมซ้ำได้) และแก้ปัญหาจริงที่จะเจอถ้าไม่ทำ: กดขอใหม่ 2-3 ครั้งแล้วได้เมนูเดิมวนซ้ำ ผู้ใช้จะรู้สึกว่า AI "โง่"
- **ความยาก:** **กลาง** — เพิ่ม state เก็บชื่อเมนูที่เคยแนะนำในรอบนี้ (`app/page.tsx`), ส่งไปเป็น param เพิ่มใน `/api/generate-recipe`, เพิ่มบรรทัดในระบบ prompt ของ `generate-recipe/route.ts` ว่า "ห้ามแนะนำเมนูที่อยู่ในรายการนี้ซ้ำ"

### F6. ปุ่มลบเมนูที่บันทึกไว้
- **แก้ปัญหาของ:** Persona B (B3)
- **ทำไมอยากได้จริง:** ลิสต์เมนูที่บันทึกจะโตขึ้นเรื่อยๆ และคนกดบันทึกผิด/เปลี่ยนใจแน่นอน (ปุ่มหัวใจกดง่าย พลาดง่าย) ตอนนี้ลบไม่ได้เลยแม้แต่เมนูของตัวเอง ยิ่งใช้นานยิ่งรกจนลิสต์ไม่มีประโยชน์
- **ความยาก:** **กลาง** — ต้องเพิ่ม delete policy ใน `supabase/migration.sql` (ปัจจุบันตั้งใจไม่มี), เพิ่ม `deleteRecipe()` ใน `lib/supabase.ts`, ปุ่มลบใน `SavedRecipes.tsx` — **ข้อควรระวัง:** RLS select policy ตอนนี้เปิด `using (true)` คือใครถือ anon key ก็ query แถวคนอื่นได้ ถ้าจะเพิ่ม delete policy ต้องคิดเงื่อนไข `user_id` ให้รัดกุม (แม้จะรู้อยู่แล้วว่ายังไม่ใช่ auth จริง 100%) ไม่งั้นใครก็ลบของคนอื่นได้เหมือนกัน

### F7. โหลดเมนูที่บันทึกไว้กลับมาทำซ้ำ (ต่อกับ RecipeCard/ChefChat)
- **แก้ปัญหาของ:** Persona B (B4)
- **ทำไมอยากได้จริง:** จุดประสงค์ของการบันทึกคือ "จะเอามาทำอีก" — ตอนนี้บันทึกได้แต่กลับมาใช้จริงไม่ได้เลย (อ่านได้อย่างเดียว) ถือเป็นฟีเจอร์ที่ทำครึ่งทาง คุณค่าที่แท้จริงของ B1/B2 จะไม่เต็มจนกว่าจะมี F7
- **ความยาก:** **กลาง-ยาก** — ตาราง `saved_recipes` ตอนนี้เก็บแค่ `recipe_name`/`ingredients: string[]`/`instructions: string[]` ไม่ครบตาม `Recipe` interface ใน `lib/types.ts` (ขาด `difficulty`, `estimated_time`, `nutritional_info`, `chef_tips`, `is_staple`) ต้องแก้ schema DB + `saveRecipe()`/`SavedRecipe` type ให้เก็บ recipe แบบเต็ม ไม่ใช่แค่ UI เพิ่มปุ่มเฉยๆ

### F8. วันหมดอายุ/ความสำคัญของวัตถุดิบ (Food waste priority)
- **แก้ปัญหาของ:** Persona A (A5) — ตรงกับ mission ประกาศไว้ของโปรดักต์มากที่สุด
- **ทำไมอยากได้จริง:** นี่คือเหตุผลที่แอปนี้ชื่อ "ล้างตู้เย็น" ไม่ใช่ "หาเมนู" เฉยๆ — คนที่ของใกล้หมดอายุจะอยากให้ AI เอาของนั้นไปใช้ก่อนของอื่น ไม่ใช่แค่ "ใช้ของที่มี" แบบสุ่มลำดับ
- **ความยาก:** **ยาก** — ต้องเพิ่ม UI ใส่วันหมดอายุ/priority ตอน add ingredient (`IngredientInput.tsx` ต้องออกแบบใหม่บางส่วน), ส่ง priority นี้เข้า prompt ของ `/api/generate-recipe`, และต้องมีที่เก็บ inventory ระยะยาวกว่าที่มีตอนนี้ (ผูกกับ F4 แต่ซับซ้อนกว่าเยอะ เพราะต้องมี validation วันที่ + คิด UX ใส่วันแบบไม่น่ารำคาญ) — เหมาะเป็นเฟสถัดไป ไม่ใช่ quick win

### ฟีเจอร์ที่ดูเท่แต่คงไม่ค่อยมีคนใช้จริง (บอกตรงๆ ตามที่ขอ)

- **Dark mode toggle** — `app/globals.css` เตรียม CSS variables `.dark {...}` ไว้ครบแล้ว แต่ไม่มี toggle จริง ฟังดูเหมือนทำง่าย (แค่เพิ่มปุ่ม toggle class) แต่ **ไม่ตรงกับ JTBD ของ persona ไหนเลย** ที่เจอในโค้ด — ไม่มีใครมาบ่นเรื่องนี้ในบริบทของแอปทำอาหารสั้นๆ ที่เปิดใช้ไม่กี่นาทีต่อครั้ง ควรเลื่อนไปทำหลังฟีเจอร์ที่กระทบ JTBD จริงหมดแล้ว
- ~~**ระบบ Auth เต็มรูปแบบ (OAuth/login)** — แก้ B5 ได้จริง แต่ effort สูงมาก (รื้อ identity ทั้งระบบ, กระทบทุกจุดที่อิง `getAnonymousUserId()`)~~ **ทำไปแล้ว 2026-07-29 — และประเมิน effort ไว้สูงเกินจริง:** `getAnonymousUserId()` ถูกใช้แค่ 2 ที่ (`saveRecipe`/`getSavedRecipes` ใน `lib/supabase.ts`) ไม่ได้กระจายทั้งระบบอย่างที่เขียนไว้ตอนแรก งานจริงคือแก้ 3 ไฟล์เดิม + เพิ่มไฟล์ใหม่ 3 ไฟล์ + SQL migration 1 ไฟล์ ไม่ต้องลง package เพิ่มเลยเพราะ `@supabase/supabase-js` มี auth ติดมาอยู่แล้ว
- **แชร์เมนูไปโซเชียล/แชร์ลิงก์ให้เพื่อน** — ฟังดูเท่และทำไม่ยาก (generate og-image + share button) แต่ไม่มีหลักฐานใน JTBD ไหนเลยว่าผู้ใช้อยากแชร์ "เมนูจากของเหลือในตู้เย็นตัวเอง" ให้คนอื่นดู (ต่างจากแอปทำอาหารทั่วไปที่โชว์ผลงาน) ความเป็นไปได้ที่จะถูกใช้จริงต่ำ
- **คำนวณโภชนาการสะสมรายวัน/รายสัปดาห์** — ต่อยอดจาก `nutritional_info` ที่มีอยู่แล้วก็จริง แต่เกินสโคปของ "ล้างตู้เย็นครั้งนี้กินอะไรดี" ไปมาก กลายเป็นแอป diet tracker คนละประเภท ผู้ใช้ที่อยาก track จริงจังมักมีแอปเฉพาะทางอยู่แล้ว (เช่น MyFitnessPal) ไม่น่าจะย้ายมาทำในนี้

## 4. ลำดับความสำคัญ (impact สูง + effort ต่ำ ก่อน)

| ลำดับ | ฟีเจอร์ | Impact | Effort | เหตุผลที่อยู่ตรงนี้ |
|---|---|---|---|---|
| 1 | **F1** — โชว์ staple vs ต้องซื้อเพิ่ม | สูง | ง่ายมาก | ข้อมูลมีอยู่แล้ว 100% แก้ไฟล์เดียว ได้ผลทันทีกับ persona หลักสุด (A) |
| 2 | **F2** — รีเซ็ต ChefChat ตอนเปลี่ยนสูตร | กลาง | ง่ายมาก | 1 บรรทัด แก้ bug เชิง UX ที่ทำให้ persona C รู้สึกแอปไม่น่าเชื่อถือ |
| 3 | **F3** — ChefChat รู้ ingredientList จริง | สูง | ง่าย | ต่อยอด prop/prompt ที่มีอยู่แล้ว ทำให้ persona C ได้คำตอบที่ personalize ขึ้นชัดเจน |
| 4 | **F4** — จำ ingredientList ไว้ข้ามเซสชัน | กลาง-สูง | ง่าย | pattern localStorage มีต้นแบบอยู่แล้วในโค้ด ลด friction ทุกครั้งที่เปิดแอปของ persona A |
| 5 | **F5** — ปุ่มขอเมนูอื่น + กันซ้ำ | กลาง | กลาง | ต้องแก้ prompt/ state เพิ่ม แต่ยังอยู่ในไฟล์เดิมที่คุ้นแล้ว |
| 6 | **F6** — ลบเมนูที่บันทึก | กลาง | กลาง | ต้องแก้ RLS ให้รอบคอบเรื่อง security ก่อนเปิดใช้ ใช้เวลาคิดมากกว่าลงมือ |
